## 3. 启动与装配（src/main.ts）

启动顺序（`src/main.ts`）：

```text
main()
 ├─ initDatabase()                     # 打开 SQLite，生成列/迁移（PRAGMA user_version）
 ├─ initRepositories(getDb())          # 初始化各 repository 单例
 ├─ initPipelineRuntime({ db, config, logger })
 │    ├─ 区域注册表加载 / 同步
 │    ├─ 构建六个 adapter（按 config 的 URL/Token）
 │    ├─ 初始化 scheduler / orchestrator / unlock / quota 等运行时
 │    └─ runtime.start()               # 启动 cron 与额度轮询
 ├─ configureCompaniesService(...)     # 公司服务依赖注入
 ├─ initUnlockEventsRuntime(...)       # 解锁 → 变更事件 → 投递运行时
 ├─ （可选）后台 worker 循环：
 │    ├─ Enrichment Worker  每 8s 取 20 条
 │    ├─ Platform Refresh  每 60s 取 20 条并生成到期刷新任务
 │    └─ Customs Worker    每 120s 取 10 条并生成到期海关任务
 └─ buildServer() → Fastify listen(127.0.0.1:LEAD_PORT)
```

- 所有 worker 轮询都是**串行不重叠**的：上一轮未结束则跳过本轮（`every()` 内的 running 标志），避免堆积。
- worker 启动失败不会让整个进程不可用：记录 error 日志，HTTP 与采集/解锁主流程仍可用。
- 优雅退出：收到 `SIGTERM/SIGINT` 后停止定时器、关闭 Fastify、关闭 DB。

**配置读取**（`src/config.ts`）：`.env` / 环境变量 / `~/.lead-platform/config.json`，zod 校验，非法配置启动即失败（fail fast）。配置项分四组：服务（端口/监听/数据目录/日志/时区）、调度与队列（cron 窗口、单轮上限、租约、并发/重试）、快照与归档（压缩算法/保留天数/归档目录/备份目录）、上游（6 个 URL + Token + fuma 账号 + 默认关键词）。完整清单见 `.env.example` 与 [14 安装部署手册 §5](14-安装部署手册.md)。

## 4. 数据访问层（src/repositories/）

设计原则：**所有 SQL 只出现在 repositories**；上层拿到的都是类型化对象，不感知表结构。仓储同时封装了三类「有状态查询」：

| 场景 | 典型实现 | 文件 |
|---|---|---|
| 任务原子领取 | `UPDATE … WHERE status='pending' AND next_retry_at<=now` + 租约字段，单语句/短事务 | `jobs.ts` |
| FIFO / 优先级 | `ORDER BY priority, created_at` 的队列扫描 | `jobs.ts` |
| 全局游标 | `seq > ? ORDER BY seq LIMIT ?`，`nextCursor` 由最后一行的 seq 生成 | `changeEvents.ts`、`companies.ts`（keyset） |
| 快照写入 | sha256 去重 + brotli 压缩 + blob 引用 | `snapshots.ts` |
| 台账 | `idempotency_key` 唯一约束插入 | `unlockLedger.ts` |

`repositories/types.ts` 定义行类型与查询输入；`repositories/index.ts` 统一构造；`sql.ts` 提供通用的分页/条件/JSON 解析工具，避免字符串拼接注入（参数化查询）。

## 5. 领域层（src/domain/）

| 文件 | 内容 | 阅读要点 |
|---|---|---|
| `normalize.ts` | 中文/英文公司名归一化（去括号噪声、统一后缀、英文去 `co.,ltd` 等） | 归一化只用于匹配/去重，不作为展示名 |
| `dedupe.ts` | 来源记录 → 公司主档归并（USCC → 归一化名 + 省市 → tanji_id） | 合并是软合并；`merged_into` 决定对外可见主体 |
| `matching.ts` | 探迹匹配打分（USCC 精确 → 名称/包含/相似度/省市/相关度），候选与置信度 | 打分参数集中在此，便于调参与单测 |
| `pagination.ts` | 不透明游标编解码与参数校验 | 客户端不应解析游标 |
| `query.ts` | 通用 WHERE/排序构造 helpers | 仅被 repositories 使用 |

这些模块不依赖 Fastify / DB / 网络，`tests/unit/domain.test.ts`、`tanji-match.test.ts` 可直接覆盖。

## 6. 适配层（src/adapters/）

统一约定：

- `adapters/http.ts`：一个 `fetch` 封装负责——超时、`Authorization: Bearer`、统一 envelope 解包（`ok/data/meta/error`）、上游错误码归一（`SOURCE_SESSION_INVALID` / `UPSTREAM_RATE_LIMITED` / `SOURCE_UNAVAILABLE` 等）、requestId 透传、指数退避重试（默认 ≤3 次）。
- 各来源适配器只负责：URL/参数拼装、响应 schema 校验、字段映射到内部结构（`SourceLead` / `PlatformProfile` / `PlatformJob`）。
- 令牌桶与最小间隔在适配器内部实现（按来源配置），解锁请求走 tanji 的优先通道。
- **测试禁止真实网络**：所有上游调用在 tests 中由 `tests/mock-upstreams/` 替代；适配器单测用注入的 fetch stub。

阅读路径：`adapters/sources/types.ts`（统一契约）→ `boss.ts`（最简单）→ `ali.ts`（分页 + 详情并发）→ `mic.ts`（无鉴权）→ `tanji.ts`（搜索/详情/联系人/解锁，错误归一最全）→ `fuma.ts`（海关 POST 查询 + 缓存/权限）。

## 7. 流水线（src/pipeline/）

| 文件 | 职责 | 要点 |
|---|---|---|
| `scheduler.ts` + `cron.ts` | 读取启用 Goal，按 cron tick 创建 Run；手动触发同一入口；单 Goal 互斥 | cron 解析与下一次触发时间计算在 `cron.ts` |
| `orchestrator.ts` | Run → source_queries → 调 adapter 流式采集 → 快照 + 公司初建 + 入队 | 单轮超时、来源跳过、run.stats 聚合 |
| `enrichment.ts` | 消费 `source_detail` / `tanji_match` / `tanji_detail` 任务 | 匹配 → 工商补全 → 投递解锁任务 |
| `unlock.ts` | 消费 `unlock` 任务：额度预检、contacts 预检、解锁、台账、联系人入库 | `waiting_quota` 恢复依赖 `quota.ts` |
| `quota.ts` | 周期观测探迹额度，写 `quota_observations`，唤醒等待任务 | 检测日刷新/结算日恢复 |
| `platformRefresh.ts` | 消费 `platform_profile` / `platform_jobs` 任务；到期任务生成 | 岗位 `active/closed/重新上线` diff |
| `customs.ts` | 消费 `customs` 任务：fuma 查询 → 名称过滤/角色分类 → 画像 | 仅 Ali/Mic；permission/no_data 分支 |
| `wiring.ts` | 组装运行时依赖（db/repositories/adapters/scheduler/workers） | 依赖注入中心，改装配看这里 |
| `ports.ts` | 定义流水线对外的窄接口（可 mock） | 便于单测替换 |
| `unlockEventsRuntime.ts` | 解锁完成 → 变更事件 → webhook/SSE 的运行时接线 | 事件链路端到端 |

**新增一个 worker/阶段**：定义 stage 常量 → 在 `repositories/jobs.ts` 的查询枚举中注册 → 实现 `runOnce` → 在 `wiring.ts` 装配 → 在 `main.ts` 挂循环 → 补单测与 OpenAPI/jobs 文档。

## 8. 事件层（src/events/）

```text
change_events（DB，seq 全局单调）
   └─ dispatcher.ts  → 按订阅 event_types 生成 webhook_deliveries → 签名投递 / 重试 / 死信
   └─ sse.ts         → /v1/events/stream 广播（Last-Event-ID 从 DB 补发）
   └─ subscriptions.ts → 订阅 CRUD（secret 脱敏返回）
   └─ signature.ts   → HMAC-SHA256(timestamp + "." + rawBody)
```

- `dispatcher.ts` 是唯一「投递副作用」出口，便于测试（mock HTTP server 验证签名/重试/死信）。
- `envelope.ts` 统一事件 envelope（`eventId/seq/type/occurredAt/companyId/version/source/data`）。
- 事件消费方语义是 at-least-once：重试可能重复，必须按 `eventId`/`seq` 去重。

## 9. HTTP / API 层（src/http/）

- `server.ts`：构建 Fastify（requestId、统一 envelope、错误处理、Bearer 鉴权钩子、无 CORS、仅监听配置的 host）。
- `routes/index.ts`：路由总装配；`routes/health.ts`（免鉴权探针）、`routes/status.ts`（运行态）、`routes/docs.ts`（`/docs`、`/openapi.json`、`/mcp-tools.json`）、`routes/contracts.ts`（契约清单）、`routes/manifest.ts`（版本/构建元信息）。
- `routes/handlers/{core,companies,ops}.ts`：按资源分组的业务 handler；`routes/helpers.ts` 提供 envelope/分页/解析公共函数。
- `routes/admin.ts`：备份 / 归档 / 校验 / 恢复 / DB 统计（本机 Bearer，仅本机使用）。
- 鉴权：除 `/v1/health`、`/docs`、`/openapi.json` 外全部要求 `Authorization: Bearer <LEAD_API_TOKEN>`；token 比较使用常量时间实现。

> 修改接口时务必同步 zod schema —— OpenAPI、MCP 工具、CLI 帮助都由同一契约生成；否则 `npm run gen:check` 会失败。

## 11. MCP（src/mcp/）

- `server.ts`：stdio MCP server，启动时读取 `LEAD_API_TOKEN` / `LEAD_BASE_URL`，**代理 REST**（不直连 DB/上游）。
- `tools.ts`：36 个 `lead_*` 工具的 schema 与 handler；服务不可达时返回 `SERVICE_UNAVAILABLE`。
- 工具清单的唯一事实源是生成的 `spec/mcp-tools.json` 与 `/mcp-tools.json`；`skills/lead/SKILL.md` 是给 Agent 的操作手册（含典型工作流与示例）。

## 12. 契约生成（scripts/gen.ts + spec/）

```bash
npm run gen          # 生成 spec/openapi.json、spec/mcp-tools.json、spec/cli-commands.json、/docs 页面数据
npm run gen:check    # 校验生成物与实现一致（CI 必须通过）
```

- 输入：`src/api/spec.ts`（路由/参数/schema 元数据）+ `src/cli/definitions.ts`（CLI 定义）+ `src/mcp/tools.ts`（工具定义）。
- 输出：`spec/*.json` 与运行时 `/docs`、`/openapi.json`、`/mcp-tools.json`。
- 示例值必须为合成数据；不得包含真实的公司/联系人/token。

├─ fixtures/             # 合成数据：公司/岗位/海关/区域（虚构，无真实 PII）

测试纪律（与 [CONTRIBUTING](../CONTRIBUTING.md) 一致）：

- **零真实网络**：所有上游调用指向 `tests/mock-upstreams`；禁止真实调用 `POST unlock`；
- fixtures 必须合成，禁止复制真实公司/联系人；
- 单测覆盖纯逻辑与错误分支；集成测试覆盖「采集 → 补全 → 解锁 → 事件」端到端；
- `npm test` 全绿 + `npm run gen:check` 通过 + `npm run typecheck` 通过，是 PR 的最低门槛。
