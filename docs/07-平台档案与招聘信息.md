# 07 · 平台档案与招聘信息（v0.4 增量设计（数据校准））

- v0.3.1（Q7）：岗位/店铺原始快照改为永久保留（brotli 压缩 + 90 天冷归档，不删除）

- 状态：待评审（与 01/02/03/04 同步冻结）
- 背景：用户要求「在公司详情里看到一家公司在各平台上的**最新状态、店铺情况、招聘信息**」。v0.1 只存来源证据 + 原始快照，不能结构化查询/展示；本文补齐这一层。
- 决策来源：2026-11-16 第四轮访谈（见 [00-需求访谈记录](00-需求访谈记录.md) 第 6 节）
- v0.3 关联：公司详情同时包含**海关画像卡片**（Ali/Mic，见 [08-海关数据补全](08-海关数据补全.md)）；Ali/Mic 的英文抬头（平台 `displayName`）用于海关查询与探迹英文匹配

## 1. 需求定义

### 1.1 要看到什么

| 平台 | 内容 |
|---|---|
| **Boss** | 公司档案（城市/地址/行业/规模/融资阶段/标签/福利/简介/logo）、在招岗位数、招聘者数/列表、**全量在招岗位**（标题/薪资/城市/区县/学历/经验/招聘人/链接）、岗位新增/下线历史 |
| **智联** | 公司档案（行业/规模/融资/城市/地址/官网/简介/标签/福利）、在招岗位数、**全量在招岗位**（标题/薪资区间/城市/区县/学历/经验/发布时间/招聘人/链接）、岗位新增/下线历史 |
| **Ali** | **店铺档案**：会员/认证等级、入驻年限、Supplier Index、评分/评价数、主营产品、经营模式、成立年份、员工数、年营收、主营市场、支付/交付条款、厂房面积、产线数、交付率、响应率/响应时间、出口额、认证标签（全量原样 + 归一化） |
| **Mic** | **店铺档案**：会员等级（diamond/gold + 起始年份）、Audited、能力星级、系统认证、业务类型（含 `trading_company`）、主营产品、成立时间、员工数、营业额、厂房面积、地址、官网（全量原样 + 归一化） |
| **Tanji** | 权威工商信息 + 联系方式（解锁，沿用 01/02 设计） |

### 1.2 展示方式

- **一期只在公司详情按平台卡片展示**（用户决策）；公司列表的「按招聘活跃/店铺等级/新鲜度过滤」暂不做，接口预留。
- 每个平台卡片包含：平台状态（active/stale/lost）、最近刷新时间、核心摘要（岗位数/招聘者/会员等级/认证）、岗位或店铺详情入口。
- **Ali/Mic 卡片同时用于海关/探迹匹配**：`displayName`（英文抬头）写入 `companies.english_name`，供 fuma 海关查询与 tanji 英文名匹配（见 08）。

### 1.3 刷新策略（用户决策）

| 对象 | 刷新频率 | 说明 |
|---|---|---|
| 新入库公司 | **即时抓全** | 第一次进入流水线时抓 4 平台档案 + 岗位 + 店铺 |
| 存量公司 · 招聘（Boss/智联） | **每周** | 全量统一降频，不分活跃度 |
| 存量公司 · 店铺（Ali/Mic） | **每月** | 全量统一降频 |
| 手动 | 随时 | `POST /v1/companies/{id}/refresh` 指定平台/类型 |
| 执行方式 | **后台刷新 worker 全天涓流** | 不能挤进 02:00 采集窗口，否则违反限频；worker 按来源令牌桶持续消费 |

> 「最新」= 最近一次成功抓取（接口返回 `lastFetchedAt` / `lastSeenAt` / `nextRefreshAt`）；上游无推送，不存在实时语义。

## 2. 数据模型（在 02 基础上新增）

### 2.1 `company_platform_profiles`（每公司 × 每平台最新档案）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | ULID |
| company_id | TEXT NOT NULL FK | companies.id |
| platform | TEXT NOT NULL | `boss` / `zhilian` / `ali` / `mic` |
| platform_company_id | TEXT NOT NULL | 平台公司 ID / account |
| display_name | TEXT NULL | 平台展示名 |
| source_url | TEXT NULL | 平台公司页/店铺 URL |
| full_name | TEXT NULL | 平台全称（Boss/智联 `fullName/registeredName`） |
| city_name / address | TEXT NULL | 平台侧城市/地址 |
| industry / scale / stage | TEXT NULL | 平台侧行业/规模/融资阶段 |
| logo_url / intro | TEXT NULL | |
| tags / benefits | TEXT NULL | JSON 数组 |
| job_count / boss_count | INTEGER NULL | Boss/智联：在招岗位数/招聘者数 |
| recruiters | TEXT NULL | JSON：招聘者列表（Boss） |
| store | TEXT NULL | JSON：Ali/Mic 店铺档案（归一化公共字段 + `raw` 原样） |
| platform_status | TEXT NOT NULL | `active` / `stale` / `lost` |
| last_fetched_at | TEXT NOT NULL | 最近一次成功抓取 |
| last_seen_at | TEXT NULL | 最近一次在检索结果中命中 |
| next_jobs_refresh_at / next_store_refresh_at | TEXT NULL | 下次刷新时间（调度用） |
| raw_snapshot_id | INTEGER NULL | 最近一次原始响应快照 |
| version | INTEGER NOT NULL DEFAULT 1 | 档案版本（平台侧变更 +1） |
| created_at / updated_at | TEXT NOT NULL | |

唯一：`(company_id, platform)`；索引：`(platform, next_jobs_refresh_at)`、`(platform, next_store_refresh_at)`、`(platform_status)`。

### 2.2 `company_platform_jobs`（岗位，Boss/智联）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | ULID |
| company_id | TEXT NOT NULL FK | |
| platform | TEXT NOT NULL | `boss` / `zhilian` |
| platform_company_id | TEXT NOT NULL | |
| job_id | TEXT NOT NULL | 平台岗位 ID（Boss `jobId` / 智联 `positionNumber`） |
| title | TEXT NOT NULL | 岗位标题 |
| salary_text | TEXT NULL | 薪资原文 |
| salary_min / salary_max | INTEGER NULL | 智联可结构化；Boss 仅原文 |
| city_name / district | TEXT NULL | |
| degree / experience | TEXT NULL | 学历/经验 |
| publish_time | TEXT NULL | 发布时间（智联） |
| recruiter_name / recruiter_title | TEXT NULL | 招聘人 |
| job_url | TEXT NULL | |
| status | TEXT NOT NULL | `active` / `closed` |
| first_seen_at / last_seen_at | TEXT NOT NULL | 首次/最近发现 |
| closed_at | TEXT NULL | 从最新在招列表消失的时间 |
| raw | TEXT NULL | 平台原始岗位 JSON（可选，压缩） |
| created_at / updated_at | TEXT NOT NULL | |

唯一：`(platform, platform_company_id, job_id)`；索引：`(company_id, platform, status)`、`(platform, status, last_seen_at)`。

**生命周期**：最新一次「在招列表」中出现 → `active` + 更新 `last_seen_at`；之前 `active` 但本次不在列表 → `closed` + `closed_at`；`closed` 岗位再次出现 → 回 `active`（保留 `first_seen_at`，产生「重新上线」变更）。岗位行永久保留（历史），原始 payload 按 4.3 节保留期清理。

### 2.3 `change_events` 扩展（平台变更并入公司日志）

新增字段：

| 字段 | 说明 |
|---|---|
| entity_type | `company` / `platform_profile` / `job`（默认 `company`） |
| entity_id | 对应实体 ID（company_id 仍保留，便于按公司查） |

平台字段路径约定（`field` 列）：

- `platforms.<platform>.<field>`：如 `platforms.boss.jobCount`、`platforms.boss.recruiters`、`platforms.ali.store.membership.label`、`platforms.mic.store.audited`；
- 岗位批量变化以聚合事件表示：`platforms.<platform>.jobs`，`old_value/new_value` 为 `{active, added, closed, total}` 摘要（避免每个岗位一条事件造成风暴）；
- 岗位级细节通过 `company_platform_jobs` 查询（`first_seen_at/closed_at` 即历史）。

对外事件类型新增：`platform.profile.updated`、`platform.jobs.updated`（与 `company.updated` 同 envelope，`companyId` 必填）。

## 3. 刷新机制与容量

### 3.1 刷新任务

- 复用 `pipeline_jobs`，新增 stage：`platform_profile`、`platform_jobs`；唯一约束调整为 `(company_id, stage, platform)`（platform 可空）。
- 触发：
  - 公司首次 `discovered` → 立即创建 4 平台 `platform_profile` + 2 平台 `platform_jobs` 任务；
  - `next_jobs_refresh_at` 到期（每周）→ 创建 `platform_jobs` 任务（Boss/智联）；
  - `next_store_refresh_at` 到期（每月）→ 创建 `platform_profile` 任务（Ali/Mic；Boss/智联档案随每周岗位刷新一起更新）；
  - 手动 `POST /companies/{id}/refresh`。
- 调度：后台 **refresh worker** 常驻，按来源令牌桶（Boss 12/min、智联 15/min、Ali 10s/页、Mic ~30/min）全天涓流执行；优先级：新公司 > 到期刷新 > 手动（手动可插队）。
- 抓取端点：
  - Boss：`GET /v1/companies/{id}`（档案/hotJobs/recruiters）+ `GET /v1/companies/{id}/jobs`（全量在招）；
  - 智联：`GET /v1/companies/{companyNumber}` + `/jobs`；
  - Ali：`GET /v1/suppliers/{companyId}`；
  - Mic：`GET /api/companies/{account}?include=audit,response,reviews`。

### 3.2 容量估算（存量 2 万家，用户口径）

- 招聘每周：20,000 家 ×（Boss 详情+岗位 2 请求 + 智联 2 请求）= 80,000 请求/周 ≈ 11,400/天；
  - Boss ≈ 5,700/天 ≈ **4 次/分钟**（限 12/min ✅）
  - 智联 ≈ 5,700/天 ≈ **4 次/分钟**（限 15/min ✅）
- 店铺每月：20,000 ×（Ali 1 + Mic 1）= 40,000/月 ≈ 1,300/天（远低于限频 ✅）
- 新公司（按 200–1000/天）：每家公司约 6 请求 ≈ 1,200–6,000/天（叠加在上方仍可承受）
- **结论**：全量降频 + 全天涓流可行；若未来缩短为「招聘每日」，20,000 家需约 100 小时/天，不可行（已与用户确认采用全量降频）。

### 3.3 平台状态判定

| 状态 | 判定 |
|---|---|
| `active` | 最近一次成功抓取 ≤ 8 天（招聘刷新周期内） |
| `stale` | 9–45 天未成功刷新 |
| `lost` | > 45 天未刷新，或详情返回 404/公司已下架（连续 3 次） |

> 公司级「是否还在该平台活跃」用 `lastSeenAt`（检索命中）+ `platformStatus` 表达，不做实时判断。

## 4. 变更与快照

### 4.1 平台变更 → 公司日志

- 每次刷新计算平台档案字段 diff → 写入 `change_events`（`entity_type=platform_profile`，`field=platforms.<platform>.<field>`，`source=source:<platform>`）。
- 岗位变化聚合为一条 `entity_type=platform_profile`、`field=platforms.<platform>.jobs` 的事件（`old/new` 含 added/closed/active 计数）。
- 对外可查：
  - 公司级：`GET /v1/companies/{id}/changes`（包含平台字段路径）；
  - 平台级：`GET /v1/companies/{id}/platforms/{platform}/changes?sinceVersion=`。
- Webhook 事件：`platform.profile.updated`、`platform.jobs.updated`（按公司聚合，一次刷新最多 1 条/类型）。

### 4.2 防风暴

- 同一刷新批次的平台变更合并为同一 `version`；
- 岗位变更不逐岗位推送，只在 `company_platform_jobs` 留历史 + 聚合事件；
- 平台档案字段只对「一等字段」产生 diff（`store`/`recruiters` 等 JSON 字段用哈希比较，变化时整块上报）。

### 4.3 原始快照保留（按类型，默认值待确认）

| 快照类型 | 保留期 |
|---|---|
| 检索页、公司详情、探迹响应 | 365 天（沿用 02） |
| **岗位列表响应** | **30 天**（归一化岗位行永久） |
| **店铺档案响应** | **永久（Q7）**：brotli 压缩 + 90 天后冷归档，不删除 |

> 原因：岗位/店铺每周/每月刷新会产生大量响应快照（2 万家 × 每周 ≈ 8 万条/周），全量长期保留体积不可控；归一化后的岗位/店铺档案永久保留，已满足「看到最新状态 + 历史变化」的需求。

## 5. 接口（详细契约见 03）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/companies/{id}?include=platforms` | 公司详情附每平台卡片摘要 |
| GET | `/v1/companies/{id}/platforms` | 全部平台最新档案摘要 |
| GET | `/v1/companies/{id}/platforms/{platform}` | 单平台完整档案（Boss/智联含招聘摘要；Ali/Mic 含店铺） |

| GET | `/v1/companies` | 一期仍只保留基础过滤（平台/状态等列表过滤预留） |

## 6. 验收标准（新增）

| # | 验收项 |
|---|---|
| AC-11 | 新公司入库后自动出现 4 平台档案卡片；Boss/智联卡片含在招岗位数与岗位列表；Ali/Mic 卡片含会员/认证/主营产品等店铺字段；`lastFetchedAt` 正确。 |
