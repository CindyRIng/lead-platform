## 1. 背景与目标

### 1.1 背景

线索（潜在客户）分散在多个 B2B 平台，且各平台客户端（boss / zhilian / ali / mic）已经封装为本地 REST 服务；探迹客户端（tanji）可提供权威工商信息与联系人解锁能力（按企业消耗额度）。目前缺少一个统一入口：按区域目标自动采集、逐条补全、聚合成公司主档，并把「新线索 / 变更 / 联系方式」以可编程方式交给下游。

### 1.2 目标

1. **一个 Goal 驱动全流程**：设置区域（省 → 地级市枚举）等条件后，自动/手动定期从四个来源采集线索。
2. **流式异步流水线**：每拿到一家公司立即进入探迹补全；不等待某个平台整批完成。
3. **权威公司主档**：以探迹工商信息为准，合并多平台来源证据；保留全量原始快照。
4. **额度感知的联系人解锁**：FIFO 队列，额度耗尽自动暂停、恢复自动续跑，绝不丢任务。
5. **完整可追溯**：字段级变更日志（老值→新值、来源、时间、run、版本号）+ 全局事件流。
6. **对外可编程**：REST + CLI + MCP + OpenAPI 3.1 + `/docs` + SKILL + Webhook/SSE。
7. **平台档案可见**：公司详情按平台卡片展示各平台最新状态、店铺情况、招聘信息（含岗位新增/下线历史）。
8. **海关画像**：Ali/Mic 线索用英文抬头经 fuma-platform 查询海关提单，补充出口/进口画像（目的国、HS、产品、买家）到公司详情。

### 1.3 非目标（一期不做）

- 不做爬虫/浏览器自动化（全部复用五个 client 的 REST）。
- 不做 CRM/外呼业务编排，不主动写 fuma-platform / Twenty CRM 的库（只发事件，下游自己消费）。
- 不做 CRM 已有客户查重（一期）。
- 不做 Web UI、不做 Postgres、不做多机分布式（单机单进程）。
- 不做区县级精确筛选（县级企业随市级结果自然覆盖）。
- 不做自动登录/验证码（登录失效时暂停并暴露状态，等待人工在 client 侧完成）。
- 不做线索评分、自动营销、数据可视化大屏。
- 不做公司列表按平台状态/店铺等级筛选（一期只在详情展示平台卡片；接口预留）。
- 不做平台数据实时刷新（上游无推送，「最新」= 最近一次成功抓取；接口返回 lastFetchedAt/nextRefreshAt）。
- 不做 Boss/智联线索的海关补全（一期仅 Ali/Mic 英文抬头路径；中文名→英文提单名匹配待评估）。

### 1.4 覆盖基线与额度规划（2026-11-16 实测校准）

河北四源真实采集结果（详见 [12-河北四源覆盖实测报告](12-河北四源覆盖实测报告.md)）：

| 指标 | 实测值 | 区间/说明 |
|---|---|---|
| 四源唯一公司（去重估算） | **≈9,586** | 9,352–9,821 |
| Mic | **5,008** | 省关键词 + 11 市关键词全量并集；详情 5008/5008 |
| Ali | **2,961** | 种子 + 两轮行业×城市扩展；估算上限 3.1–3.3k（无官方全量） |
| Boss / 智联 | 1,188 / 1,261 → 去重 **2,375** | 仅第 1 页；深翻页会更高 |
| Ali∩Mic | 459 | 英文名精确/近精确 |
| 招聘↔Ali/Mic 重叠 | ≈299 | tanji 抽样 3.75%（95% CI 0.8–6.7%） |

**由此产生的硬约束（必须写进设计）**：

1. **解锁额度远小于覆盖量**：个人月额度 1,500（当前剩余 223，结算日 11 号），全量解锁 9,586 家需 ≈6.4 个月。一期必须按优先级解锁（招聘在招 > 平台付费/认证会员 > 有海关出口记录 > 其余），不能全库 FIFO。
2. **一次性补全耗时**：探迹匹配+详情 9,586 家 ≈8h + ≈8h（20/min）；海关 7,510 家 ×4 查询 ≈12.5h（可多日分散）。
3. **刷新容量按实测 9,586 校准**（原设计按 2 万家留余量）：招聘周刷 ≈680 请求/天、店铺月刷 ≈250/天、海关月刷 ≈1,001/天，均远低于限频。
4. **Ali 名称启发式 1,330 家（45%）建议上线前做详情核验**（约 15–25 分钟 + 缓存）；未核验线索只入工商库、不优先消耗解锁额度。
5. **验收基线**：一次河北全量 Run 应产出 ≥8,500 家唯一公司（Ali ≥2,600、Mic ≥4,500、招聘 ≥2,000），详见 AC-18。

## 2. 名词与术语

| 术语 | 含义 |
|---|---|
| Goal | 目标设置：区域 + 平台 + 关键词 + 上限 + 频率 + 优先级 +（预留）外贸条件 |
| Run | 一次 Goal 执行（cron 或手动触发），包含若干 source_queries 与流水线任务 |
| Source lead | 某个平台某次抓取中的一条公司记录（存原始快照） |
| Company | 线索聚合后的公司主档（唯一主体，跨平台合并） |
| Snapshot | 原始抓取数据（检索页 / 平台公司详情 / 探迹搜索结果 / 探迹详情）不可变副本 |
| Change event | 公司主档的字段级变更（含来源、旧值、新值、版本） |
| Enrichment | 探迹匹配 + 工商补全（不消耗额度） |
| Unlock | 探迹解锁企业联系人（1 家 = 1 额度点，业务幂等） |
| FIFO | 解锁队列按「发现时间」先到先解锁 |
| waiting_quota | 解锁任务因额度不足进入的等待状态，恢复后自动续跑 |
| 来源证据 | 公司出现在某平台某关键词/某城市检索结果中的事实（用于解释与打标签） |
| 平台档案 Platform Profile | 每家公司 × 每个平台的最新结构化档案（公司状态、店铺、招聘摘要），独立于工商主档 |
| 平台岗位 | Boss/智联在招岗位快照（含 first_seen/closed_at 生命周期） |
| 海关画像 | Ali/Mic 公司经 fuma-platform 查得的提单聚合（样本统计）：出口/进口记录数、目的国/来源国、HS、产品、买家/供应商、置信度 |
| 刷新 worker | 后台常驻任务：按「新公司即时 / 招聘每周 / 店铺每月」抓取平台档案与岗位，全天按限频涓流执行 |

## 3. 用户与场景

| 角色 | 诉求 |
|---|---|
| 运营/业务负责人 | 设置区域目标、查看每日新增线索与解锁进度、发现异常（登录失效/额度耗尽） |
| 下游 Agent | 通过 REST/MCP 增量拉取新公司、变更、联系人；订阅 webhook 实时消费 |
| 下游系统（fuma / Twenty CRM / 外呼） | 消费事件/游标，把线索写入自己的业务闭环（LeadPlatform 不直接写它们） |
| 开发者/运维 | 部署 systemd 服务、看 `/status`、处理登录/额度故障、备份恢复 |

**核心用户故事**

1. 作为运营，我创建「河北省」Goal 并勾选 4 个平台；手动点一次「运行」，2 小时后我能在 `GET /v1/companies?province=河北省` 看到新公司列表。
2. 作为下游 Agent，我订阅 `company.created` / `contact.unlocked` webhook；收到事件后按 `companyId` 拉详情。
3. 作为下游同步程序，我每天用 `GET /v1/changes?sinceSeq=N` 增量拉变更，保证本地副本与 LeadPlatform 一致。
4. 作为运维，探迹额度耗尽时我看到 `unlock` 任务全部 `waiting_quota`、`/v1/quota` 告警；额度恢复后无需人工干预自动续跑。
5. 作为运营，我发现某公司匹配到了错误的探迹主体，调用 `POST /v1/companies/{id}/rematch` 重新匹配并保留纠正历史。

## 4. 功能需求（FR）

> 编号规则：FR-x；每条包含「要求」与「验收要点」。优先级 P0 = 一期必须有。

### FR-1 Goal 管理（P0）

- 创建 / 查询 / 更新 / 启用停用 / 归档 Goal。
- 字段：
  - `region`：省（必填，如「河北省」）+ 可选城市子集（缺省 = 全省所有地级市枚举）。
  - `platforms`：`["boss","zhilian","ali","mic"]` 子集。
  - `keywords`：按平台配置；Boss/智联默认 **10 个** `["外贸","外贸业务员","外贸经理","外贸单证员","国际贸易","跨境电商","外贸跟单","外贸专员","海外销售","国际业务"]`（Q6 覆盖分析建议扩展）；Mic 按省检索（无关键词）；Ali **按省全量枚举，行业关键词仅本地打标签/二次筛选**（不作为覆盖手段）。
  - `max_leads_per_run` / `daily_lead_limit`：线索条数上限（空 = 不限）。
  - `schedule_cron`：默认 `0 2 * * *`（Asia/Shanghai）。
  - `time_window`：可选执行时间窗（默认夜间）。
  - `priority`：整数（一期单 Goal，字段预留）。
  - `trade_filter`：预留 JSON（一期默认 null，不启用过滤）。
- 验收：Goal 创建后能在 `GET /v1/goals` 看到；非法区域/平台/关键词返回 `VALIDATION_ERROR`。

### FR-2 调度与触发（P0）

- 每个 Goal 按 cron 每日触发；同时支持 `POST /v1/goals/{id}/run` 手动触发。
- **任务不重叠**：同一 Goal 上一轮 `running` 时，新触发被拒绝（`RUN_IN_PROGRESS`）或排队（可配，默认拒绝）。
- 单轮最长时长默认 6 小时（可配）；超时后停止采集并标记该 run `partial`，已入队任务继续执行。
- 每个 run 有独立的 platform query 进度、统计、错误。
- 验收：手动触发后 `GET /v1/runs/{id}` 能看到 `running → completed/partial`；重复触发返回明确错误。

### FR-3 线索采集（P0）

- 按「平台 × 地级市 × 关键词」拆分检索任务；Ali/Mic 按「平台 × 城市」检索（Mic 城市为客户端过滤）。
- **Ali 覆盖策略（Q6 实测）**：扩展种子（3 省 + 11 市 + 115 县）+ **行业词 × 城市 strict 矩阵**；当前可发现 **2,961**（129 种子 1,799 + 矩阵/扩展净增 1,162）；两轮扩展增量 +663→+328，估算上限 3.1–3.3k；名称启发式线索需详情核验。
- **Mic 覆盖策略**：按省 + 11 市关键词并集全量枚举（实测 **5,008 家**；详情 5008/5008 已拉取）。
- **Boss/智联覆盖策略**：默认关键词扩展至 10 个（Q6），11 市 × 10 词；本轮仅第 1 页即得 **1,188 / 1,261**（去重 2,375），深翻页可更高；只覆盖「正在招聘」的公司。
- Run 统计增加**覆盖度指标**：`uniqueCompanies`、`crossSourceOverlap`、`coverageByCity`、`keywordYield`（见 11 文档第 4 节）。
- 深度：**能翻多少翻多少**（受各 client 上限与限频约束；Boss/智联 `pages≤5` 单次，但可按 queryId 继续翻页）。
- 每拿到一家公司**立即**落原始快照并投递流水线任务（流式，不整批等待）。
- 严格遵守每个上游 client 的限频与页间隔（见 NFR-3）。
- 采集前检查来源健康：`loggedIn=false` / 会话失效 → 跳过该来源、记录 `source.session_invalid` 状态，不阻塞其他来源。
- 验收：Run 统计中能看到每平台 query 数、页数、线索数；某平台登录失效时该 Run 仍能完成其他平台。

### FR-4 快照与去重（P0）

- **全量原始快照**：检索页、平台公司详情、探迹搜索结果、探迹详情均存不可变快照（append-only，payload 压缩 + 内容哈希去重）。
- 平台记录与公司主档分离：`company_sources` 记录 (platform, platform_company_id) ↔ company 的映射。
- **公司去重规则**（详见 02 文档）：
  1. 有 USCC：USCC 相同 → 同一公司；
  2. 无 USCC：规范化公司名相同 + 省/市相同 → 同一公司；
  3. 探迹匹配成功后以 `tanji_company_id` 归并；
  4. 无法判定 → 新建公司（保留来源证据），后续匹配到再合并（`company.merged` 事件）。
- 验收：同一家公司出现在 Boss 与智联时，只产生一个 company、两条 company_sources；快照按 run 可追溯。

### FR-5 公司主档与工商补全（P0）

- 优先用平台详情中的 USCC（Boss/智联）做探迹精确搜索；无 USCC 用公司名搜索。
- 匹配：总是自动取最佳匹配，同时保存候选列表 + 置信度 + 匹配时间（`match_meta`）。
- 探迹工商字段写入公司主档（USCC、法人、注册资本、成立日期、地址、省市、经营状态、行业、规模、经营范围、官网、联系方式计数等）。
- 匹配不到（`unmatched`）：公司仍入库（保留来源快照），后续 run 可重试；不消耗额度。
- 验收：`GET /v1/companies/{id}` 返回工商信息、匹配置信度、候选、来源证据。

### FR-6 联系人解锁队列（P0）

- 所有 `tanji_matched` 且未解锁的公司进入 FIFO 解锁队列（按 `first_seen_at` 排序）。
- 每次解锁前检查额度（tanji `/v1/status`）；有额度则 `POST /v1/companies/{id}/unlock`（`idempotencyKey`），1 家 1 点。
- 已解锁公司不重复扣额度（依赖 tanji 业务幂等，`alreadyUnlocked=true`）。
- `QUOTA_EXHAUSTED` → 任务转 `waiting_quota`，队列暂停；按可配间隔轮询额度（默认 10 分钟），检测到日额度刷新或结算日过后自动恢复。
- 不设每日上限（用户决策）；额度耗尽自动暂停、恢复自动续跑。
- 解锁成功后拉取联系人并入 `company_contacts`，产生 `contact.unlocked` 事件。
- 验收（可用 mock 上游模拟）：额度耗尽时任务处于 `waiting_quota` 且不丢；模拟额度恢复后自动变为 `unlocked`；`unlock_ledger` 有完整扣点记录。

### FR-7 变更日志与事件（P0）

- 公司主档每次变更产生**字段级**变更事件：字段、旧值、新值、来源、run、时间、版本号（公司内单调递增）。
- 全局事件序号 `seq` 单调递增，`GET /v1/changes?sinceSeq=N` 可增量拉取。
- 对外事件类型：`company.created`、`company.updated`、`contact.unlocked`、`platform.profile.updated`、`platform.jobs.updated`（一期）。
- Webhook 订阅：注册/停用/查看；事件投递 HMAC-SHA256 签名、指数退避重试、死信可查可重放。
- SSE：`GET /v1/events/stream` 实时推送（可选过滤事件类型）。
- 验收：修改一个公司字段 → 产生带旧值/新值的变更事件；webhook 收到签名正确的投递；失败重试可见。

### FR-8 对外查询（P0）

- 公司列表：按省/市/平台/解锁状态/变更时间/关键词过滤，游标分页。
- 公司详情：主档 + 来源列表 + **各平台档案卡片（`include=platforms`）** + 最近快照摘要 + 联系人 + 当前版本 + 匹配信息。
- 变更历史：`GET /v1/companies/{id}/changes?sinceVersion=` 完整字段级历史（含平台字段路径）。
- 快照：`GET /v1/companies/{id}/snapshots`（按来源/时间筛选）。
- 平台档案：`GET /v1/companies/{id}/platforms`、`/platforms/{platform}`、`/platforms/{platform}/jobs`、`/platforms/{platform}/changes`（详见 FR-12）。
- 验收：见第 8 节验收标准 AC-4/AC-5/AC-11。

### FR-9 运行态、健康与额度（P0）

- `GET /v1/runs` / `/v1/runs/{id}`：运行状态与平台/城市级进度。
- `GET /v1/sources`：五个上游的健康、登录态、限频/最近错误。
- `GET /v1/quota`：探迹三层额度、结算日、近 7 天解锁数、最近观测时间。
- `GET /v1/status`：本服务版本、DB、队列积压、调度状态、告警预留字段。
- 验收：任一上游不可用时 `/v1/sources` 显示对应状态；额度耗尽时 `/v1/quota` 可见。

### FR-10 CLI / MCP / 文档 / SKILL（P0）

- CLI `lead`：goal / run / company / event / source / quota / status 子命令，`--json` 输出与 REST envelope 一致。
- MCP：`lead_*` 工具集，覆盖查询、Goal 管理、手动触发、事件拉取；默认代理 REST（不另起进程）。
- `/docs` 自包含 HTML、`/openapi.json`（OpenAPI 3.1）、`/mcp-tools.json`。
- SKILL 包：给 Agent 的工作流说明（与五个 client 的 SKILL 风格一致）。
- 验收：REST 与 CLI/MCP 结果一致；OpenAPI 可导入。

### FR-11 手工干预（P1）

- `POST /v1/companies/{id}/rematch`：重新匹配探迹主体（记录纠正历史、更新匹配信息）。
- `POST /v1/companies/{id}/unlock`：把该公司提到解锁队列之前（人工优先级）。
- `POST /v1/runs/{id}/cancel`：取消运行中 Run（正在执行的上游请求完成后停止）。
- `POST /v1/jobs/{id}/retry`：重试失败任务。
- `POST /v1/companies/{id}/refresh`：手动刷新平台档案/岗位（可指定平台与类型，插队执行）。
- 验收：rematch 后变更日志有记录；manual unlock 不破坏 FIFO 统计；refresh 能立即触发刷新。

### FR-12 平台档案与招聘信息（P0）

- **每公司 × 每平台最新档案**（`company_platform_profiles`）：
  - Boss/智联：平台公司名、URL、城市/地址、行业/规模/阶段、logo/简介/标签/福利、在招岗位数、招聘者数/列表；
  - Ali/Mic：店铺档案（会员/认证等级、年限、Supplier Index、评分、主营产品、经营表现等；全量原样 JSON + 常用字段归一化）。
- **岗位**（Boss/智联，`company_platform_jobs`）：全量在招岗位（标题/薪资/城市/区县/学历/经验/发布时间/招聘人/链接）+ `active/closed` 生命周期与 first_seen/closed_at 历史。
- **刷新策略**：新公司即时抓全；存量招聘每周、店铺每月（全量统一降频）；后台刷新 worker 全天按限频涓流执行，与 02:00 采集 Run 解耦；支持手动刷新。
- **展示**：公司详情 `include=platforms` 返回每平台卡片摘要（状态/岗位数/招聘者/会员等级/最近刷新时间）；单平台接口返回完整档案与岗位列表。
- **平台变更**：平台字段变化以 `platforms.<platform>.<field>` 写入公司变更日志；岗位变化聚合为 `platforms.<platform>.jobs` 摘要事件；推送 `platform.profile.updated` / `platform.jobs.updated`。
- **快照保留**：岗位列表响应 30 天、店铺档案响应 90 天（归一化岗位/档案永久）。
- **验收要点**：
  - 新公司入库后 4 平台卡片可见（Boss/智联含岗位数、Ali/Mic 含店铺摘要）；
  - 二次刷新后岗位新增/下线可追溯（`status=closed` + `closed_at`）；
  - 刷新计划可查（`nextJobsRefreshAt`/`nextStoreRefreshAt`），手动 refresh 生效；
  - 平台变更进入公司变更日志并可被 webhook 收到。
- 详细设计见 [07-平台档案与招聘信息](07-平台档案与招聘信息.md)。

### FR-13 海关数据补全（P0，限 Ali/Mic）（v0.3）

- **触发**：Ali/Mic 线索完成平台详情（拿到英文抬头）并完成探迹匹配后，创建 `pipeline_jobs(stage=customs)`。
- **查询**：fuma-platform `POST /v1/customs/query`，`accountId` 使用配置的 fuma 账号；以英文抬头为主查询名，查询 `companyFlag=1`（进口视图）与 `2`（出口视图）各第 1 页（20 条），记录 `totalNum/allCount/cached/source`。
- **过滤与聚合**：按名称 token 过滤提单，分类「公司作为出口商 / 进口商」；聚合出口/进口记录数、日期范围、目的国/来源国、HS 前 4 位、产品、买家/供应商 Top 列表、样本重量/件数；输出 `confidence`（high/medium/low/none）与 `sampled=true`。
- **入库**：写 `company_customs_profiles`；原始响应落 `raw_snapshots(kind=fuma_customs_query)`；字段变化产生 `customs.*` 变更事件与 `customs.updated` 事件。
- **刷新**：新公司即时；存量每月（与店铺档案同步）；手动 `POST /v1/companies/{id}/customs/refresh`。
- **边界**：Boss/智联一期不做；`totalNum` 不是精确提单量；低置信度画像仍可查但不推送。
- **验收要点**：AC-14/AC-15/AC-16；详见 [08-海关数据补全](08-海关数据补全.md)。

## 5. 业务规则（BR）

| 编号 | 规则 |
|---|---|
| BR-1 区域 | 区域注册表以 GB/T 2260 为准（省/地级市）；四平台各自映射（Boss cityCode / 智联 code / Ali code / Mic 英文名）。详见 04 文档「河北省映射样例」。 |
| BR-2 外贸证据 | 不强制过滤；为公司打 `trade_tags`（如 `source_keyword:外贸`、`platform_export_supplier`、`boss_job:外贸业务员`）。一期不调用探迹海关资质校验。Goal 预留 `trade_filter`，后续可开启。 |
| BR-3 去重 | USCC 优先；无 USCC 用「规范化名 + 省市」；探迹匹配后以 `tanji_company_id` 归并；合并产生 `company.merged`。 |
| BR-4 匹配 | 顺序：USCC 精确 → 名称完全匹配 → 名称近似 + 同省/市 → 探迹相关度分。最佳候选写入主档，候选 + 置信度留痕；支持 rematch。 |
| BR-5 额度 | 解锁 1 家 = 1 点；搜索/详情/工商免费；已解锁不重复扣；额度耗尽 → waiting_quota；恢复自动续跑；台账记录每次扣点。 |
| BR-6 入库时机 | 探迹工商补全后立即入库（`enrichment_status=tanji_enriched`，`unlock_status=pending`）；联系人解锁后增量更新。 |
| BR-7 快照 | 每次抓取都保留原始快照（检索页/详情/探迹响应）；内容哈希去重；默认保留 365 天；变更事件永久。 |
| BR-8 变更 | 仅在字段值实际变化时产生变更事件；同一批次变更共享一个版本号；公司 `version` 单调递增；事件 `seq` 全局单调。 |
| BR-9 调度 | 每日 02:00 起跑（Asia/Shanghai）+ 手动为主；同一 Goal 不重叠；单轮最长 6h（可配）。 |
| BR-10 失败 | 上游可重试错误 → 指数退避重试（最多 N 次）→ 死信；登录失效/风控 → 跳过该来源并标记不健康，不自动登录。 |
| BR-11 安全 | 仅监听 127.0.0.1；Bearer 鉴权；PII（手机/邮箱/联系人）仅 Bearer API 明文返回，日志脱敏；token 文件 0600。 |
| BR-12 时区 | 调度按 Asia/Shanghai；DB 存 UTC ISO 8601；接口返回带偏移时间。 |
| BR-13 平台档案 | 新公司即时抓全；存量招聘每周、店铺每月刷新；刷新 worker 全天涓流、与采集共享上游限频；「最新」= 最近一次成功抓取，接口返回 `lastFetchedAt`/`nextRefreshAt`。 |
| BR-14 岗位生命周期 | 最新在招列表出现 → `active`；消失 → `closed` + `closed_at`；再次出现 → 回 `active`。岗位行永久保留，原始载荷按类型保留。 |
| BR-15 平台变更 | 平台字段变化 → `platforms.<platform>.<field>` 变更事件（并入公司日志）；岗位变化聚合为一条摘要事件；平台状态 active ≤8 天 / stale 9–45 天 / lost >45 天或连续 3 次 404。 |
| BR-16 海关补全 | 仅 Ali/Mic；英文抬头 → fuma 海关（flag 1/2）；样本聚合、标注 sampled；不消耗探迹额度；原始响应保留 90 天。 |
| BR-17 解锁前置 | 先查 tanji contacts：`unlocked=true` 直接取明文不调用 unlock；`unlocked=false` 才入 FIFO 解锁队列。 |
| BR-18 英文匹配 | Ali/Mic 探迹匹配用英文抬头（记录候选/置信度），中文名仅作校验参考。 |

| NFR-8 安全 | 仅 loopback；Bearer token；文件权限 0600；不在日志/错误信息中输出明文联系人；无外部遥测。 |
| NFR-9 兼容 | Node >= 22.5（与现有五件套一致）；Linux（NixOS）systemd user service；无 Docker 依赖。 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 探迹月度额度被一次性耗尽 | 当月无法继续解锁 | 用户已知悉接受；`waiting_quota` 挂起 + 恢复自动续跑；`/v1/quota` 可见；后续可加每日上限配置项 |
| Boss/智联登录态过期 | 采集中断 | 采集前预检；失效即跳过并标记；不自动登录；状态接口/日志可见（后续可接告警） |
| 上游风控/验证码 | 请求失败/封禁 | 严格限频；识别 `verification.pending` / 风控状态即暂停该来源；尊重 client 的 cooldown |
| 探迹误匹配 | 解锁浪费额度 | 候选 + 置信度留痕；rematch 接口；USCC 优先 |
| 全量快照存储膨胀 | 磁盘压力 | gzip + 哈希去重；按类型保留期（岗位 30 天/店铺 90 天/其它 365 天）；容量估算见 02 |
| 存量平台刷新积压 | 「最新」不新鲜 | 招聘每周、店铺每月全量降频；刷新 worker 全天涓流；手动 refresh 插队；`next*RefreshAt`/`platformStatus` 可观测 |
| 岗位数据时效性 | 招聘信息变化快 | 每周刷新为基线；高价值公司可手动 refresh；接口明确返回 lastFetchedAt，不做实时承诺 |
| 海关模糊匹配噪声 | 画像失真/买卖家名单错 | 名称 token 过滤 + 角色分类 + 置信度；低置信度不推送；保留 matchedSample 供复核 |
| 英文抬头与注册名不一致 | 海关/探迹匹配偏差 | 保留 queryNames 与候选；tanji 英文匹配记录置信度；必要时人工 rematch |
