# 21 · 监督运行与每日批次（风控严格模式）

> 适用日期：2026-11-19 起。目标：自动运转 + 外部 watchdog + 极低上游频率，绝不无人值守全速跑。

## 1. 运行结构

```text
systemd timers
  ├─ lead-daily-batch.timer  → 每日 02:00 触发一个城市批次（外部控制器）
  └─ lead-watchdog.timer     → 每 15 分钟检查上游/队列/数据，异常自动熔断
LeadPlatform service         → API + enrichment/refresh/customs workers
```

- **不启用** LeadPlatform 内置 scheduler；批次完全由外部控制器触发。
- 每日只跑 1 个城市，顺序：石家庄 → 唐山 → 秦皇岛 → 邯郸 → 邢台 → 保定 → 张家口 → 承德 → 沧州 → 廊坊 → 衡水。
- 每批平台：Mic + 智联 + Ali 城市地理种子；**首轮不含 Boss**，Boss 待专项复核后再加入。

## 3. 关键文件

| 文件 | 作用 |
|---|---|
| `scripts/daily-batch.mjs` | 每日城市批次：建临时 Goal、手动触发、轮询、写报告、推进状态 |
| `scripts/watchdog.mjs` | 外部 watchdog：检查六源健康/风控、任务失败、队列、额度；异常写 PAUSE 并停 lead-platform |
| `scripts/day1-canary.mjs` | Day1 单次探活金丝雀 |
| `~/.lead-platform/daily-plan-state.json` | 下一城市、notBefore、历史 |
| `~/.lead-platform/monitor-latest.json` | 最近一次监控快照 |
| `~/.lead-platform/reports/` | 每日批次、异常、监控 JSON |
| `~/.lead-platform/PAUSE` | 熔断标记；存在时 daily-batch 不启动 |

## 4. 日常命令

```bash
systemctl --user status lead-platform
systemctl --user list-timers | grep lead-
journalctl --user -u lead-platform -f
journalctl --user -u lead-watchdog.service -n 50 --no-pager
node ~/lead-platform/scripts/watchdog.mjs        # 手动跑一次监控
cat ~/.lead-platform/monitor-latest.json
ts=$(ls -t ~/.lead-platform/reports/daily-batch-*.json | head -1); echo "$ts"
```

## 5. 熔断与恢复

watchdog 发现以下情况会自动：
1. 写 `~/.lead-platform/PAUSE` + `INCIDENT`；
2. 停止 `lead-platform`（阻断后续 Tanji/Boss 调用）；
3. 在 watchdog 报告中列明原因。

**不要自动删除 PAUSE。** 人工确认风控解除、修复问题后：

```bash
systemctl --user start lead-platform
rm -f ~/.lead-platform/PAUSE ~/.lead-platform/INCIDENT
node scripts/watchdog.mjs
```

## 6. 手动批次

```bash
# 正常：受 notBefore 限制
node scripts/daily-batch.mjs
# 强制立即跑当前城市（debug/补跑）
node scripts/daily-batch.mjs --force
# 指定城市下标（0=石家庄）
node scripts/daily-batch.mjs --force --index=0
```
