## 3. 安装与启动（实现后）

```bash
cd ~/lead-platform
npm ci
npm run build
cp .env.example .env          # 填 LEAD_API_TOKEN + 上游 token
npm start   # 首次启动自动建库/迁移（幂等）
systemctl --user daemon-reload
systemctl --user enable --now lead-platform.service
```

`systemd/lead-platform.service`（示例，实现时放入仓库）：

```ini
[Unit]
Description=lead-platform (local lead aggregation platform)
After=network.target

[Service]
Type=simple
WorkingDirectory=%h/lead-platform
EnvironmentFile=%h/lead-platform/.env
ExecStart=/usr/bin/env node %h/lead-platform/dist/main.js
Restart=on-failure
RestartSec=5
TimeoutStopSec=40

[Install]
WantedBy=default.target
```

> 注意：上游五个 client 必须已运行；LeadPlatform 只做 HTTP 调用，不持有浏览器/profile。

## 4. 健康检查与日常巡检

```bash
curl -s http://127.0.0.1:8793/v1/health
TOKEN=$(jq -r .apiToken ~/.lead-platform/config.json)
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8793/v1/status | jq
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8793/v1/sources | jq
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8793/v1/quota | jq
```

巡检清单（建议每日一次）：

| 检查 | 期望 |
|---|---|
| `/v1/status` status=ok、队列积压可接受 | pending/waitingQuota 数量合理 |
| `/v1/sources` 五源状态 | boss/zhilian `ok`（登录态未过期）；ali/mic `ok`；tanji `ok` |
| `/v1/quota` | 明确当前剩余额度；waitingQuota 是否在增长 |
| 最近 Run | `completed/partial`，无长时间 `running` |
| dead jobs | `GET /v1/jobs?status=dead` 数量为 0 或已处理 |
| 平台刷新 | `/v1/status.refresh` 的 due 是否持续增长；`/v1/sources` 无长期 degraded |
| 海关补全 | `/v1/customs/cache/stats` 命中率；`/v1/companies/{id}/customs` 抽查；fuma 账号 active |
| Webhook 死信 | `GET /v1/webhooks` 各订阅 deliveries 无大量 `dead` |
| 覆盖度 | Run 统计的 `uniqueCompanies / coverageByCity / keywordYield` 与河北基线（≈9,586）对比，偏差 >20% 时检查上游变化 |
| 磁盘 | 数据目录 + 归档目录增长与剩余空间（实测口径压缩后 5–10 GB/年，设计余量 10–20 GB/年；永久保留，建议 ≥500 GB 空闲） |

> 一期不接外部告警；上述项通过 `/v1/status.alerts` + 日志暴露。后续接入告警时复用事件类型（见第 7 节）。

## 5. 故障 Runbook

### 5.1 上游登录失效（Boss / 智联）

- 症状：`/v1/sources` 对应平台 `session_invalid`；Run 中该平台 query 被 `skipped`；日志 `source.session_invalid`。
- 原因：Boss 会话约 5 天、智联约 1 月；LeadPlatform 不自动登录。
- 处理：
  1. 在对应 client 侧完成登录（人工扫码/短信）：
     - `boss`：`POST /v1/session/login`（扫码/短信）→ 轮询 `GET /v1/session/login/{id}`；
     - `zhilian`：`POST /v1/session/login` → `GET /v1/session/login/{id}`；如有 `verification.pending` 需处理 `GET /v1/verification`。
  2. 确认 `GET /v1/status` 的 `loggedIn=true`。
  3. LeadPlatform 下一轮 Run 会自动重试该来源（无需人工恢复队列）；`source_health` 在下次探测时恢复。

### 5.2 探迹额度耗尽（预期内）

- 症状：`/v1/quota` 剩余为 0；`/v1/status.queue.waitingQuota` 增长；日志 `unlock.quota_exhausted`。
- 处理：无需人工；Quota Poller 每 10 分钟探测，日额度刷新或结算日（11 号）过后自动把 `waiting_quota` 任务恢复为 `pending`，FIFO 续跑。
- 可选：如需避免月度额度一次性耗尽，设置 `LEAD_UNLOCK_DAILY_CAP=50`（预留配置，默认空）。
- 说明：仅解锁联系人消耗额度；采集/工商补全继续正常进行。

### 5.3 采集卡住 / 队列积压

- 检查 `GET /v1/runs/{id}` 的 platform 进度、`GET /v1/jobs?status=running` 的租约。
- 常见原因：上游限频冷却、client 验证码、单轮超时。
- 处理：
  - 上游恢复后自动继续（任务 `pending` 重试）；
  - 如进程僵死：`systemctl --user restart lead-platform`（租约过期后任务自动接管，不重复扣额度）。

### 5.4 上游风控 / 验证码

- 症状：`/v1/sources` 平台 `degraded`/`verification_pending`；日志 `upstream.rate_limited` / `captcha`。
- 处理：在 client 侧完成验证（`GET /v1/verification` + `POST /v1/verification/solve` 或人工）；LeadPlatform 冷却结束后自动重试。不要通过提高并发「硬扛」。

### 5.5 Webhook 死信

```bash
lead webhook deliveries <id> --status dead
lead webhook replay <id> <deliveryId>
```
- 检查订阅方 URL 可达、签名校验逻辑（`X-Lead-Signature`）、返回 2xx。
- 死信记录永久保留直至重放成功/人工删除。

### 5.6 SQLite 维护

```bash
# 一致性检查
sqlite3 ~/.lead-platform/lead.db "PRAGMA integrity_check;"
# 备份（在线，WAL 安全）
sqlite3 ~/.lead-platform/lead.db ".backup '$HOME/lead-platform-backup-$(date +%F).db'"
# 历史数据永久保留：不按年龄删除；手动触发冷归档（默认 90 天自动）
lead admin archive --before-days 90 --dry-run
lead admin archive --before-days 90
lead admin restore --month 2026-11        # 从冷归档恢复某月到 hot 库
lead admin archive verify                 # 校验归档清单 sha256 与可读性
# 收缩（归档后）
sqlite3 ~/.lead-platform/lead.db "VACUUM;"
```
- 备份建议：每日一次 + 升级前一次；保留最近 7 份。
- 不直接编辑 DB；schema 变更只通过 `src/db/schema.sql` + `src/db/migrate.ts`（启动时自动执行，`PRAGMA user_version` 版本化、只增不改）。

### 5.7 进程崩溃恢复

- `systemctl --user restart lead-platform`；启动时自动执行迁移（幂等）。
- 未完成任务：租约（60s）过期后重新领取；解锁依赖 `idempotencyKey` + 探迹业务幂等，**不会重复扣额度**。
- 校验：`/v1/status` 的 queue 数量、最近 Run 状态。

### 5.8 平台刷新积压 / 数据不新鲜

- 症状：`/v1/status.refresh.due` 持续增长；平台卡片 `lastFetchedAt` 超过周期（招聘 >8 天、店铺 >35 天）；`platformStatus=stale/lost` 增多。
- 常见原因：上游登录失效/风控冷却（刷新 worker 无法请求该来源）；单轮采集占满限频；进程重启导致调度延迟。
- 处理：
  1. 先看 `/v1/sources` 定位是哪个来源不健康（登录/验证码 → 按 5.1/5.4 处理）；
  2. 临时提高刷新频率不可取（会触发风控）；必要时手动刷新重点公司：`lead company refresh <companyId> --platforms boss --kinds jobs`；
  3. 确认 `LEAD_REFRESH_WORKER_ENABLED=true`，重启后 due 队列会自动续跑（租约接管，不丢任务）；
  4. 容量核对（实测 9,586 家校准）：招聘周刷 ≈680 请求/天、店铺月刷 ≈250/天、海关月刷 ≈1,001/天；2 万家设计余量仍保留。若 due 长期积压，检查是否被采集 Run 抢占了限频（考虑错峰或延长刷新时段）。

### 5.9 fuma 海关故障 / 无数据

- 症状：`/v1/companies/{id}/customs` 返回 `failed` / `status=no_data`；日志 `customs.permission_denied` / `customs.upstream_error`；`/v1/sources.fuma` 异常。
- 排查：
  1. `GET http://127.0.0.1:17890/v1/status`：账号是否 active；`GET /v1/customs/cache/stats`：缓存是否正常；
  2. `permission_denied` → 检查 `FUMA_ACCOUNT_ID` 账号的海关数据权限（fuma 侧）；
  3. `totalNum=0` → 属正常无数据（不重试）；低置信度（中文名查询/名称歧义）→ 保留 `no_data/low confidence`，不推送；
  4. 上游错误/超时 → 退避重试（≤3 次）；仍失败标记 `failed` 并跳过，不影响平台档案/解锁主流程；
  5. 需要人工补查：`lead company customs-refresh <companyId>`（fuma 缓存 24h 内重复查询免费）。
- 容量：Ali/Mic 新公司 200–1000/天 × 4 查询 ≈ 800–4,000 次/天；若积压，先检查 fuma 账号在线状态与串行限速。

### 5.10 历史数据归档与磁盘（Q7：永久保留）

- 原则：**不按年龄删除任何历史数据**；只做「brotli 压缩 + 冷热分层」。
- hot：近期快照留在 SQLite（`raw_blobs.body` brotli 压缩）；默认 90 天后由 archive 任务移到 `~/.lead-platform/archive/YYYY-MM/`（brotli 文件），`raw_snapshots.archived=1` + `archive_path` 指向文件；清单存 `meta_kv.archive_manifests`（文件、条数、字节、sha256）。
- 查询：归档快照对普通 API 透明（按需从归档读取/恢复）；`lead admin restore --month=YYYY-MM` 恢复到 hot 库。
- 校验：每月 `lead admin archive verify`；备份策略覆盖 `lead.db` + `archive/` 目录（不可只备份 DB）。
- 容量（实测校准）：一次性补全 ≈0.3–0.6 GB（压缩后）；年度刷新约 5–10 GB/年；设计余量 10–20 GB/年，5 年约 50–100 GB。磁盘不足时**扩容/迁移归档盘**，不得删数据。变更事件永久保留在 DB（可选按年压缩归档，但保留可查询索引）。

### 5.11 Ali 扩展采集（手动补量，可选）

- 目的：Ali 无省级全量目录；需要补量时用 `exploration/2026-11-16-coverage-crawl/ali-expand.mjs`（地理种子 / 行业×城市矩阵）。
- 批次：每约 **40 次查询冷却 60s**（防详情接口临时风控）；两轮扩展实测增量 +663 / +328，持续递减。
- 监控：`/v1/status` 的 Ali `risk.state/cooldownUntil`；出现 `CAPTCHA_REQUIRED/RATE_LIMITED` 立即停批并等待冷却。
- 当前基线：Ali 2,961；估算可发现上限 3.1–3.3k。扩展结果写入 `data/ali-expansion.json`（断点续跑）。

## 6. 安全与合规

- 仅 loopback；不得将 8793 暴露到 LAN/公网（如需，必须另行加 TLS 与来源限制，属于二期）。
- Bearer token / webhook secret 文件 0600；日志脱敏手机号/邮箱。
- 联系人明文仅 Bearer API 返回；`/docs` 不含真实数据。
- 原始快照含上游公司信息：按保留期清理；公司删除接口（P1）用于个人信息删除请求。
- 备份文件不进入 git 仓库。

## 7. 告警事件（预留，一期不接外部通知）

| 事件 | 触发 |
|---|---|
| `source.session_invalid` | 采集前预检登录失效 |
| `source.verification_pending` | 上游验证码/风控 |
| `quota.exhausted` | 探迹额度耗尽，队列进入 waiting_quota |
| `run.failed` / `run.partial` | 运行失败/部分完成 |
| `job.dead` | 任务进入死信 |
| `webhook.delivery_failed` | Webhook 重试耗尽 |
| `customs.permission_denied` / `customs.upstream_error` | fuma 海关权限/上游异常（海关补全暂停，主流程继续） |
| `customs.updated` | 海关画像刷新完成且置信度 ≥ medium（供下游订阅） |

- 一期通过 `/v1/status.alerts` + 结构化日志体现；后续接入飞书 webhook/邮件时，从 `change_events` 派生同类事件即可，无需改核心。

## 8. 容量与升级

- 容量（实测校准）：河北基线 ≈9,586 家；快照压缩后一次性 ≈0.3–0.6 GB、年度刷新 ≈5–10 GB/年；公司主档设计余量 10 万级无明显压力。
- 升级流程：`git pull` → `npm ci` → `npm run build` → `systemctl --user restart lead-platform`（启动时自动迁移）→ 健康检查。
- 版本兼容：DB migration 只增不改（字段可加、表可加）；对外 API 以 `/v1` 前缀冻结，破坏性变更升 `/v2`。
